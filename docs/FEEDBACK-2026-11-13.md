# dsh-chronicle 产品与趋势反哺报告（2026-11-13 / v2.4.2）

> **本报告解决什么**：`docs/AUDIT-2026-11-13.md` 回答的是「代码有没有病、病治好没有」；这份回答的是「**它到底该是什么产品、还差什么**」。
> **三方视角合并**：① 主审（工程审计 + 22 项修订，工程分 7.9/10）② 重度使用者兼开发者（行为数据）③ 趋势研究员（赛道位置 + 12 个月判断）。
> **口径**：凡「实测」都是读源码与真实数据算的；样本是 5 天 / 1 个用户 / 且这个用户同时在开发它——这是本报告最大的局限，见 §7。
> 只读分析，未改任何被测数据。

---

## 0. 一页结论

**工程已经过关，产品定位错配。** 它对外宣称是「会话记忆 / 日志 / 周报系统」，真实身份是「**人类发言的编年史 + 事实索引**」——两者之间的差距不是加功能能补的。

三组最刺眼的实测：

1. **正常使用日它只被调用 1 次。** 11-12 全天调用 `chronicle_close` 1 次、查询 0 次；70 次调用里 69 次（98.6%）发生在我开发或审计它的日子。
2. **「记忆」的三个核心机制全部空转。** 事实 92 条里跨天复现 `repeated` 1 条、被推翻 `supersededBy` **0 条**、未答问题 8 条全开着；`hits>0` 10 条（10.9%），而真实「被读过」的次数是 **3**（全期 3 次 `chronicle_search`）。
3. **写了 87.2%，能用的 12.8%，证据里 0%。** 13,649 条事件中工具类 11,908 条（87.2%）；而**全部 130 个产物引用都指向 `kind:'user'` 事件，`toolresult` 被引用 0 次**——因为采集层就把 toolresult 正文丢了（只留 `ok` 布尔）。

**结论**：把定位从「记忆系统」降级为「**可审的决策台账 + 周报**」，不需要重写代码；继续按「记忆」做才需要，而那条路上它正在被平台原生化（Claude Code `/insights`、Codex `~/.codex/memories/`）从上方挤压。

**综合评分：工程 7.9 / 10 · 产品 6 / 10。** 差距集中在同一处：**它把「自检」做成了肌肉，把「被使用」留成了假设。**

### 1.4 实体层与噪声

- 实体页 **28 个，其中 20 个是源码/配置文件名**（`api.js.md`、`close.js.md`、`p2-scoring.test.mjs.md`…）= 71%。我要的是「这个项目现在什么状态」，不是每个文件的流水页。
- 事件 13,649 条：`tool` 5,915 + `toolresult` 5,993 = **87.2%**；`user` 238 + `assistant` 1,503 = 12.8%。
- 会话 **20 个，被产物引用过 14 个，从未被引用 6 个（30%）**。
  > 趋势研究员给的是 5 个（17.5%），口径不同（它按「事件占比加权」且排除了低事件量会话），以本表 30% 为准。

### 1.5 唯一每轮进上下文的机制，现在不可读

用当前 92 条事实真实跑 `buildInjectLine`（`lib/recall.js`），80 字符预算输出的实际内容是：

```
[chronicle] 空态文案统一口径：同一卡片内多张表空态文案保持一致，落一条约定避免「暂无」与「这段时…；部署与依赖双约束（部署架构或目标环境变化时重新…
```

两段都在半句被硬切，第二段没有任何可执行信息。**这是全仓库性价比最高的一处修改。**

## 2. 三方视角：分歧在哪、合流在哪

| 视角 | 它看重什么 | 结论 | 与另外两方的关系 |
|---|---|---|---|
| 主审（工程） | 契约、数据正确性、性能外推 | 22 项 + 复审 3 项全修；P0 清零；工程 7.9 | 证明**它能被修**，但没回答「该不该有」 |
| 重度用户（行为） | 我每天真实怎么用它 | 日常 0 查询 ⇒ 价值全在被动产出 | 把「修好了」翻译成「还是没人用」 |
| 趋势（赛道） | 对手、替位、12 个月演化 | 真差异化是「可审」，但审的是人不是 agent | 解释了「为什么没人用」：赛道位没占对 |

**三方合流的三个动作**（我作为用户的建议与趋势研究员的 D1/D2/D3 高度重合，取交集）：

1. **把事实层导出成任何 agent 都能消费的指令文件**（对齐 `AGENTS.md` + 输出相对上次的 diff）——用户视角的「周报」，趋势视角的 D1。
2. **修注入行，让「读」发生在不用读的地方**（一条一行、优先 `detector`/`expiresWhen`、按标点断句、注入也记 `hits`）——用户视角的「别占我上下文还给我乱码」，趋势视角的 D3。
3. **用工具噪声换「可回答的动作账本」**（只留 `ok:false` 正文；成功的折叠成 `(tool, target, count)`）——用户视角的「43.6% 行数没人读」，趋势视角的 D2。

## 3. 定位建议：把「记忆系统」降级为「可审的决策台账」

### 3.1 三条会被证伪的现有叙事

| 叙事（现状） | 会被什么证伪 | 依据 |
|---|---|---|
| 「不替代实时工作记忆，只做冷记忆」 | 会被追问成「连记录层也没占住」 | 87.2% 写入不可查询；平台原生日/周报正在吃掉记录层 |
| 「可审的编年史」 | 被问「审的是谁的行为」 | 130/130 引用是 user 事件，`toolresult` 引用 0 次——**审的是人的决策，不是 agent 的行为** |
| 「每天自动收口」 | 生产执行次数为 0 | `state.json` 的 `lastClose.reason = "manual"`，4 天全对得上手工调用 |
| 「事实层两个分区互不污染」 | 数据直接反驳 | 33 条自身事实里 30 条在 `general`，流进主索引与规则导出 |

### 3.2 四条不会被证伪的护城河（要往这里加码）

**零第三方依赖 · 纯 Markdown · 可 git diff · 卸载后数据仍在可脱离宿主带走。**
这四条恰好是云端记忆层（Mem0/Zep）和平台原生能力做不到的——它们给不了「一份能带走的文件」。

### 3.3 一句话新定位

> 不是「记住你」，是「**替你留一份三个月后还能查出当时为什么那么定的账**，顺便每周给你一段能直接贴出去的话」。

## 4. 六个月路线图（做三件 / 砍三件）

评分口径：趋势分 = 方向上是否越来越值钱；可行分 = 以现有代码量能否在 6 个月内做到（5 分制）。

### 做

**D1. 事实层 → 可被任何 agent 消费的指令文件（趋势 5 / 可行 5）**
现状已有 80% 零件：`chronicle_export_rules`、`expiresWhen`、`detector`、`scope`。缺两件：**导出格式对齐 `AGENTS.md`**、**输出「本次导出相对上次改了什么」**。
风险：`expiresWhen` 66% 空、`detector` 78% 空 ⇒ 导出的会很薄，**必须与 D3 同批做**。
验收：`chronicle_export_rules` 产出可直接放进 `AGENTS.md` 的段落；连续两次导出的 diff 能被 git 看见。

**D3. 修注入行（趋势 4 / 可行 5）**
一条一行不拼接；优先「有判别信号 / 有失效条件」的条目；按标点断句；`injectBudget` 语义写死「一行一条」，建议 140 字；**注入被采用时记 `hits`**。
验收：`buildInjectLine` 输出无「…；」式断句；注入行的 `hits` 能在面板看到。

**D2. 工具噪声 → 可回答的动作账本（趋势 5 / 可行 4）**
只保留 `ok:false` 的 toolresult 正文（截断 + 脱敏），成功的折叠成 `(tool, target, count)`；`ops_bash` 占工具调用 **53.3%**（3,160/5,915），优先按「命令族 + 退出码」聚合。
风险：会动 `chronicle_doctor` 的类型分布自检与 **210 条测试基线**。
验收：事件体积降 ≥40%，且「某天为什么失败」能一句话答出来。

### 砍

**C1. 砍检索复杂度（趋势 3 / 省 5）**：400 行 recall + IDF + 实体 2 跳 + 60 天半衰期，5 天被用 3 次。保留「按天/按项目浏览 + 一个 search」，**砍掉图检索**。
守门指标：30 天内 `search` ≥ 20 次，或出现一次「找回 30 天前结论」的成功案例，否则不恢复。

**C2. 冻结纪传体（趋势 2 / 省 4）**：实体页与图谱不再新投资，砍 `entityRule` 三档配置。保留只读可视化，否则面板会显得空——用「本周周报」当首屏补这个空。

**C3. 砍配置面与多档打分（趋势 3 / 省 3）**：21 项配置 + rule/llm 双档 + `followModel`/`scoringModel`/`llmTimeout`/`promptVersion` 收敛为「跟当前模型跑一次，失败退规则」。保留 `rule` 作为降级（离线部署需要），删的是**可选档位的显式配置**。
理由：多档打分让「同一天两次收口结果不同」成为可能，直接损伤「可审」这唯一卖点。

## 6. 我作为重度使用者的判断（保留个人判断色）

- **我会留着它**，但理由不是「它能记住我」，而是 11-12 那天我什么都没做、它替我省下的那次回忆。
- **我不会再为「检索」买单**：我一周 0 次查询；我要的是「三个月后能查出那天为什么那么定」，这在周文件里已经有了雏形。
- **我最想要的三个改动**：① 周报能一键导出成能贴出去的段落（D1）；② 注入行别占着上下文还给我乱码（D3）；③ 失败那天能一句话说清（D2）。
- **我最不想要的新功能**：更多召回公式、更花的图谱、更多配置项。

## 7. 风险与局限（读结论前请先读这段）

1. **样本只有 5 天 / 1 个用户，且这个用户同时在开发它**。最干净的一天（11-12）只贡献 1 次调用——这既是本报告最强的证据，也是最脆弱的证据。
2. **`client.js`（1,462 行）面板侧未审计**，面板真实使用率仍是未知；本报告谈「面板该换首屏」是基于推断而非数据。
3. **采纳 D2/C1 会动 210 条测试基线**，而「4 天 13 个版本」的发版节奏本身就是 D1/D2 的反面——动手前要先把节奏降下来。
4. **本报告的分歧点已标注**：会话覆盖率我用 30%（口径：去重会话数），趋势研究员用 17.5%（口径：事件占比加权），两者不矛盾但不可混用。
5. **`CHANGELOG` 里的「208 条测试」不是漂移**（那是 2.4.0 当时的真实值）；真正的文档漂移是 **README 写「176 条测试」**，实际 210 —— 已在本报告落盘时一并修正（README:20）。
